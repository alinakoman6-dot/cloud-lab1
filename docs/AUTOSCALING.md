# Автоматичне масштабування

## Політика

| Параметр | Значення |
|---|---|
| Тип політики | Target tracking (`lab2-cpu-target-tracking`) |
| Кластер / сервіс | `lab1-ecs-cluster` / `lab1-app-service` |
| Метрика | `ECSServiceAverageCPUUtilization` (середній CPU усіх копій) |
| Цільове значення | 60% |
| Cooldown на додавання (`ScaleOutCooldown`) | 60 с |
| Cooldown на вилучення (`ScaleInCooldown`) | 300 с |
| Мінімум / максимум копій | 1 / 3 (`min_capacity = 1`, `max_capacity = 3`) |

Target tracking працює як термостат: AWS сам створює два CloudWatch-алерти (AlarmHigh і AlarmLow) і тримає середній CPU біля 60%. AlarmHigh додає копії, коли CPU вище цілі кілька хвилин поспіль, AlarmLow прибирає копію, коли CPU довго нижче цілі.

## Чому ціль 60%

- Нова копія з'являється не миттєво: потрібні метрика, рішення політики, запуск контейнера й проходження health check в ALB. Весь цей час навантаження тримають наявні копії. Запас у 40% дозволяє пережити цей проміжок, поки CPU не дійшов до 100%.
- При цілі 80–90% запасу майже нема, і до появи нової копії сервіс уже перевантажений.
- При цілі 30–40% копії здебільшого простоюють, а ми платимо за зайві.

## Cooldown

Cooldown — час після зміни кількості копій, протягом якого політика не робить наступну зміну в той самий бік. Нова копія лише поступово забирає навантаження, тому метрика ще якийсь час показує старе високе значення. Без паузи політика додавала б копії далі, хоча вже вистачає.

- `ScaleOutCooldown = 60` — після додавання копії хвилину не додаємо наступну.
- `ScaleInCooldown = 300` — після вилучення п'ять хвилин не вилучаємо наступну. Вилучення робимо обережніше, бо помилка тут болючіша для користувачів.

Якби cooldown дорівнював 0, кількість копій могла б постійно «гойдатися» вгору-вниз (flapping), а кожен холодний старт і кожне вилучення викликали б стрибки латентності.

## Що відбувається з запитами при вилученні копії

1. Автомасштабування зменшує desired count, ECS вибирає копію для зупинки.
2. ALB знімає її з target group і перестає надсилати нові запити. Поточні запити мають час завершитися (deregistration delay).
3. ECS надсилає контейнеру SIGTERM, і gunicorn завершує поточні запити та зупиняється. Якщо контейнер не завершився за `stopTimeout`, ECS надсилає SIGKILL.

## Чому копія з'являється не одразу після перетину порогу

1. ECS публікує CPU раз на хвилину, і метрика з'являється в CloudWatch із затримкою.
2. AlarmHigh потребує кількох точок поспіль вище цілі.
3. Після рішення Fargate виділяє ресурси, завантажує образ і запускає контейнер.
4. ALB надсилає трафік лише після успішних health check.

У пробному прогоні від перетину порогу до рішення політики минуло близько 3–4 хв, а від рішення до Running — близько 30 с.

## Чому вилучення відбувається значно пізніше за падіння навантаження

AlarmLow вимагає тривалого періоду з низьким CPU (AWS навмисно робить зменшення повільним, щоб не створювати копію знову через кілька хвилин). До цього додається `ScaleInCooldown` і час на завершення поточних запитів. У пробному прогоні навантаження скінчилося о 18:10:46, а рішення про вилучення було о 18:29:55, тобто через ~19 хв. Тому між прогонами треба чекати, поки Running повернеться до 1.
